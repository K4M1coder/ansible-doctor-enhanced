# Checklist: i18n (Internationalization) Requirements Quality

Purpose: Validate the i18n feature specification (`specs/005-i18n-support/spec.md`) for clarity, completeness, consistency, traceability, and measurable acceptance criteria. Each item tests the *requirements text* itself (not an implementation) and references spec sections when applicable.

- [x] CHK001 - Are the exact output directory naming rules for language-based docs specified? [Completeness, Spec §Output Structure]
- [x] CHK002 - Is the config schema for languages (`languages.default`, `languages.enabled`, `languages.fallback`, `languages.detect_system`) fully specified with types and constraints? [Clarity, Spec §Configuration Schema]
- [x] CHK003 - Is the behavior for `languages.detect_system: true` explicitly defined (which locale codes are accepted, mapping of system locale -> language code)? [Clarity, Spec §User Scenarios US11, TC-006]
- [x] CHK004 - Are the CLI flags `--language` and `--languages` described with precedence rules over config file and exact semantics (single vs multiple languages)? [Clarity, Spec §CLI Examples, SC-005]
- [x] CHK005 - Does the spec define where translation files are loaded from and the exact file path conventions (embedded, `.ansibledoctor/translations/`)? [Completeness, Spec §TranslationLoader]
- [x] CHK006 - Is fallback precedence (embedded < project custom < collection custom < role custom) clearly specified and algorithmically described? [Clarity, Spec §TranslationLoader]
- [x] CHK007 - Are translation merging rules and override semantics (deep merge vs shallow replace) defined for nested keys? [Completeness, Spec §TranslationLoader]
- [x] CHK008 - Are the YAML translation file format requirements and validation rules given (UTF-8, characters allowed, reserved keys)? [Clarity, TC-005]
- [x] CHK009 - Is the translation format for plurals clearly defined (e.g., `one`/`other` keys) and how languages beyond English should be handled? [Clarity, SC-010]
- [x] CHK010 - Does the spec define the fallback behavior for pluralization when a language does not define `one`/`other`? [Ambiguity, SC-010]
- [x] CHK011 - Is the `t(key, **kwargs)` Jinja2 signature defined (return type, behavior on missing key, variable substitution pattern)? [Clarity, Spec §i18n TemplateFilter, SC-003, SC-009]
- [x] CHK012 - Are the rules for nested key resolution (e.g., `meta.author.name`) specified including which separators are permitted and conflict handling? [Clarity, SC-008]
- [x] CHK013 - Is the performance target for multi-language generation explicitly measurable (expected single-language baseline + per-language overhead), and listed as acceptance criteria? [Measurability, SC-006]
- [x] CHK014 - Does the spec require thread-safety for `t()` and define how to validate it (integration tests, concurrency tests)? [Coverage, TC-008]
- [x] CHK015 - Are caching rules (what gets cached, cache invalidation policy per-session) explicitly specified and measurable for reuse across languages? [Completeness, TC-002]
- [x] CHK016 - Are there explicit examples that show the generated `docs/lang/{code}/...` layout for roles, collections, and projects, including slug rules and integration across specs? [Clarity/Traceability, Spec §Output Structure]
- [x] CHK017 - Does the spec define behavior for missing translation keys (log warning + fallback to fallback language + final fallback to key)? [Clarity, SC-007]
- [x] CHK018 - Is the case of invalid language codes handled and defined (error vs skip vs use default)? [Edge Case Coverage, TC-006]
- [x] CHK019 - Do the acceptance criteria include integration tests for collection and project levels that will use i18n (cross-feature coverage)? [Coverage, Spec §Dependencies]
- [x] CHK020 - Are integration scenarios described where translation files are overridden at different depths (project-level custom translations override embedded, collection-level override project? confirm exact precedence)? [Consistency, Spec §TranslationLoader]
- [x] CHK021 - Is the expected CLI help and examples updated and exact (command strings, flags, expected default) in the spec? [Completeness, Spec §CLI Examples]
- [x] CHK022 - Are the error and warning messages for missing translation files/keys precisely specified and localizable (i18n of the messages) or left as English-only? [Clarity/Edge Case, SC-007]
- [x] CHK023 - Are constraints/assumptions for i18n implementation explicitly listed (YAML only, no gettext, no RTL in this version)? [Completeness, Spec §Out of Scope]
- [x] CHK024 - Is the translation merging precedence and custom-file discovery algorithm traceable to a single source-of-truth requirement in the spec (who makes the final decision worded unambiguously)? [Consistency/Traceability, Spec §TranslationLoader]
- [x] CHK025 - Are the test requirements for verifying pluralization, variable substitution, and nested keys defined with scenarios and expected outputs (testable examples)? [Acceptance Criteria Quality, SC-008/SC-009/SC-010]
- [x] CHK026 - Does the spec describe the expected behavior when generating multi-language for an existing output directory (overwrite vs merge; how to safely run multiple languages without inadvertently removing content)? [Edge Case, SC-004]
- [x] CHK027 - Are performance test scenarios described with concrete data sets (role complexity, number of lines or tasks) and thresholds for pass/fail? [Measurability, SC-006]
- [x] CHK028 - Are the dependencies and preconditions for the i18n feature listed and validated (Feature 002 TemplateEngine exists and supports `t()`; Feature 004 collection & outputs ready)? [Dependencies & Assumptions, Spec §Dependencies & Prerequisites]
- [x] CHK029 - Have the security considerations been addressed (no injection via variables in translation entries, YAML parsing safety, encoding/escape rules)? [Edge Case/Non-Functional, Spec §Security]
- [x] CHK030 - Is the documentation of how to add new languages (files, structure, fallback) clear, including migration guidance for teams adding languages? [Clarity/Completeness, Spec §Roadmap Impact/Output Structure]
